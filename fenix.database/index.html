Install

  1. In Fenix, press SPC h x to open the Extensions page.
  2. Search for Database browser, and install it. Fenix shows what it may do before it installs anything.

Or download the package and run fenix --install-extension fenix.database-1.3.0.fenixext.

What it may do

Fenix holds it to these, and shows them before installing it. Everything else is closed to it.

Opens network connections (TCP and UDP sockets) to these addresses
  • ${setting:database.connections} those the setting database.connections holds
  • *:5432 any host, this port
  • *:3306 any host, this port
  • *:1433 any host, this port
Reads and changes the files in your project
Sees where you are in the editor, and changes what you're editing
Reads and keeps secrets in Fenix's secret store, under these keys
  • database.password.*
  • database.passwords

About

Connect to a database, browse its schema and run statements without leaving Fenix. SQLite files, PostgreSQL, MySQL and MariaDB, and SQL Server.

SPC o b (database.open) opens the browser: your saved connections in a sidebar, each one's schema under it once it's connected -- schemas, tables and views, their columns with their types, indexes and keys -- and beside them what the last statements you ran gave back.

Connections                 │ dev  2 statements · 14 ms
                            │ 1 Rows 2   2 Done
● dev   PostgreSQL · ready  │
  ▾ app                     │ id  name   email  score
    ▾ Tables (2)            │ ─────────────────────────
      ▾ users            6  │  1  ada    a@x     1.50
          id   integer · PK │  2  grace  NULL    2.25
          name text         │
        ▸ Indexes (2)       │
        ▸ Keys (1)          │
○ prod  PostgreSQL · production
○ shop.db   SQLite          │ name text  row 1 of 2
                            │ ada

A .sqlite, .sqlite3, .db or .db3 file opens straight into it, however you open it.

No database at hand? Database: a sample database to try it on (database.sample, from the command palette) makes one: a small shop's customers, products, orders and their items, in SQLite, as sample.db in the browser with its tables open. It needs no server and nothing installed, and it's made afresh each time you run it -- kept in the extension's own folder, never in your project.

Learning it

The tutorial (SPC h T) has a lesson for it, The database browser, under Database: the browser and its sidebar, a table's rows sorted and filtered, a .sql buffer on a connection, the statement under the cursor run, its results, the history, and picking a buffer's connection. It practises on the sample database, so it goes through to its end with nothing installed; its keys are said as your key scheme has them (Fenix 1.5).

Connections

database.connections holds them, a row each: a name, the engine (sqlite, postgres, mysql -- MariaDB too -- or mssql), the host and port (left out: the engine's own), the database (a SQLite file's path, in the project: /project/data/app.db), the user, and options:

OptionWhat it does
readonlyNothing that changes what's stored runs on it -- refused here, and the session's read-only too (PostgreSQL's default_transaction_read_only, MySQL's SET SESSION TRANSACTION READ ONLY; a SQLite file opened read-only)
productionA statement that changes what's stored is asked about first
tls=preferTLS if the server offers it: PostgreSQL's and MySQL's default
tls=requireTLS or nothing
tls=strictSQL Server's TDS 8: TLS from the first byte (SQL Server 2022, Azure SQL)
tls=offNone
insecureA server certificate taken whoever signed it: a server of yours

A password is asked for when you connect, the prompt showing dots, and once it signs in it's kept in the system's keychain -- Windows' Credential Manager, the macOS Keychain, the Secret Service on Linux -- as database.password.<name>, and not asked for again (database.keep_passwords off: kept until Fenix closes). One the server refuses is forgotten and asked for again; Database: forget the password kept for a connection forgets one. The older map database.passwords (connection, password; FENIX_DATABASE_PASSWORDS, as JSON, overrides it) is still read, after the keychain.

An UPDATE or DELETE without a WHERE is asked about on any connection.

Running statements

In a .sql buffer:

KeyWhat it does
SPC m r, with standard keys also Ctrl+EnterRun the statement under the cursor -- or the selection, its statements in turn
SPC m RRun every statement in the buffer
SPC m cPick the connection the buffer runs on
SPC m hThe history: the statements you ran, newest first, searched as you type; one picked goes in at the cursor
SPC m nA new query buffer
SPC m bThe browser

A buffer runs on the connection its first lines name (-- connection: dev), else the one you picked for it, else the only one connected. The modeline says which, and how it is (db dev · ready).

Statements are split where the engine splits them: at ; outside quotes, quoted names and comments; PostgreSQL's dollar quoting ($$ ... $$, $body$) and nested comments; MySQL's # comments, backslashes in strings and DELIMITER; SQL Server's [names] and GO lines; SQLite's trigger bodies.

With standard keys, SPC is Ctrl+K: the menu is Ctrl+K m. On the browser, ? lists its keys, and a .sql buffer's as the key scheme you use has them, and yours where you rebound them: SPC m with Vim keys, C-k m and C-Enter with standard keys. Its empty results and the modeline name them the same way. It needs Fenix 1.5 or later (extension API 1.5).

Results

A statement's rows are a table, a tab a statement (1-9, [ ]):

KeyWhat it does
h j k l, the arrowsA cell; J K a screen, g G the first and last row
sSort by the column: up, down, as they came. Numbers sort as numbers, NULLs last
v VSelect cells, rows
yCopy the cell, or the selection (a tab between cells)
YCopy the row, or the selected rows, as CSV with the header
x XEvery row as CSV, as JSON, in a buffer beside
w WEvery row to a file in the project, CSV or JSON
TabThe sidebar, and back
HThe history

The focused cell is shown whole below the table, its column's type beside its name.

Table view

Enter on a table in the sidebar pages through its rows, by its key's order:

KeyWhat it does
n p, PageDown PageUpThe next page, the last
/Filter: a WHERE's condition (score > 1 AND name LIKE 'a%'); Enter on nothing, every row
e, Enter, a double clickChange the cell: the UPDATE it makes, keyed by the row's primary key (SQLite's rowid when there's none), is shown, and runs on y
DSet the cell NULL, the same way
rRead the page again
s v V y YAs in the results

A table without a primary key isn't changed here: there's no telling its rows apart.

Completion

In a .sql buffer, from the connected schema: tables (and schemas) after FROM, JOIN, INTO and UPDATE; a table's columns after table. or alias.; the statement's tables' columns elsewhere; and keywords.

Engines

  • SQLite, through Turso's engine: SQLite in Rust, which builds for WebAssembly with no C compiler and reads and writes the file itself. A file in the project is opened where it is; one elsewhere is copied and opened read-only. Turso writes through a WAL: a file that kept a rollback journal is put back as it was once a change is written (the log checkpointed into it and removed, its header saying so again). Turso is still in beta; what it doesn't do yet it says.

  • PostgreSQL: its protocol (v3), TLS asked for with an SSLRequest, SCRAM-SHA-256, md5 or a cleartext password; statements you run go as one simple query, a table view's as an extended one (Parse, Bind, Execute), which the server holds to one statement.

  • MySQL and MariaDB: the handshake, TLS asked for with an SSLRequest, caching_sha2_password (fast, or in full: over TLS, or to the server's RSA key) and mysql_native_password, auth switches; COM_QUERY, several statements at once.

  • SQL Server: TDS 7.4 -- PRELOGIN, LOGIN7 with SQL Server's own sign-in, SQL batches, a batch a statement -- and TDS 8 with tls=strict.

Checked against real servers: PostgreSQL 16, MariaDB 10.11, MySQL 8.4 (caching_sha2_password in full to the RSA key and fast, plain and with TLS) and SQL Server 2022 (TDS 7.4 unencrypted: the schema, every common type, a table view's pages and changes). TDS 8 hasn't been: the test server wouldn't take a strict connection with its self-signed certificate.

For coding agents

Two tools for your coding agents (Fenix 1.1), in the database toolset:

ToolClassWhat it answers
database_schemareadA connection's schemas, tables and views, each column's type and whether it's nullable, primary, unique and foreign keys, indexes -- or one table's (table)
database_queryreadThe rows of one statement that only reads (SELECT, WITH, VALUES, TABLE, SHOW, DESCRIBE, EXPLAIN), as JSON: at most limit (100, up to 1000)

Both take connection, a name from database.connections or an open SQLite file's; left out, it's the one the .sql buffer you're in runs on, the one you ran on last, or the only one there is. A connection that needs a password asks you for it, as the browser does.

database_query refuses whatever it can't tell only reads: more than one statement, anything but those above, SELECT ... INTO, a WITH that changes rows, EXPLAIN ANALYZE, FOR UPDATE, and functions with effects (nextval, pg_terminate_backend, advisory locks, large objects, dblink, sleep, load_file, OPENROWSET, xp_ and sp_ procedures). What passes runs on a session of its own, opened read-only -- PostgreSQL's default_transaction_read_only, MySQL's SET SESSION TRANSACTION READ ONLY, a SQLite file opened read-only -- so a transaction you have open is never touched, and the server refuses a write all the same. Each one is in the history, marked as a coding agent's.

SQL Server has no read-only session, and it needs no ; between statements, so there the check is the only safeguard and it's stricter: every word that starts a statement (DECLARE, SET, BEGIN, IF, UPDATETEXT...) is refused, unless it's a name in [brackets], as are a second SELECT outside a UNION, EXCEPT or INTERSECT, and NEXT VALUE FOR. For more certainty, give an agent's connection a login that can only read.

Limits

  • TLS on SQL Server is TDS 8's only. TDS 7 carries TLS inside its PRELOGIN packets, which Fenix's sockets, which do TLS themselves, can't; a server that forces encryption is reached with tls=strict (SQL Server 2022 and Azure SQL), or not. Windows sign-in (SSPI, Kerberos) isn't spoken, nor is Entra ID.

  • PostgreSQL: SCRAM-SHA-256-PLUS (channel binding), GSSAPI and SSPI aren't spoken; a password isn't SASLprep'd.

  • MySQL: MariaDB's ed25519 and other plugins aren't spoken.

  • A SQLite statement runs inside the call Fenix gives it, which its manifest makes a minute: one that takes longer than database.timeout (30 seconds; 55 at most) is stopped, and the browser waits meanwhile. A file outside the project is a copy, read-only, and its -wal isn't read with it.

  • Rows kept: database.max_rows (5,000) a result; a table view's page, database.page_rows (200).

  • No keychain (Linux without the Secret Service): a password kept goes to settings.toml as plain text, which Fenix says on its output page. On Linux the first one read may wait on the keychain's unlock prompt.

What it may do

  • Open sockets to the servers in database.connections, and to any host on 5432, 3306 and 1433, for a row that leaves its port out.

  • Read and keep secrets database.password.*, a connection's password each, in the system's keychain; read the older database.passwords.

  • Take up to a minute a call (limits.call_ms), for a SQLite statement.

  • Read and write the project's files: a SQLite file in it, an export.

  • Read and change the buffer you're in: a .sql buffer's text, the cursor and the selection; a statement from the history typed at the cursor (editor = "write").

  • Be told which buffer has the focus (events = ["focus"]), for the modeline.

Its own folder takes no permission: the history, which connection each buffer runs on, a copy of a SQLite file from outside the project, and the sample database are kept there. 1.4.0 asks for nothing new.

Building

cargo xtask pack extensions/database dist
cargo test --manifest-path extensions/database/Cargo.toml

cargo test checks statement splitting and the kinds of statements the safety rules go by, the rules themselves, each engine's protocol against byte sequences -- hand-made from the protocol's documents, and captured from PostgreSQL 16 and MariaDB 10.11 (src/testdata) -- SCRAM-SHA-256 against RFC 7677's example, the scrambles, TDS's types, the catalog put together into a schema and its tree, SQLite files made by SQLite itself (Python's sqlite3) read and written and their journal put back, the UPDATE builder and table pages, completion, history, the pages' keys and layout -- their hints naming the keys of the scheme in use, on the test kit's fake host -- the sample database made, made afresh and read, and what agents are given: the read-only guard, the schema and rows as JSON, and their session closed when its connection's row changes.

The tutorial's lesson (tutorial/browser.toml) is data. It was checked against Fenix 1.5's lesson format -- its fields and its checks -- but, as with any lesson, the way to be sure is to go through it in Fenix, in a fresh profile.
