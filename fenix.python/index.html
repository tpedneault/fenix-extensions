Install

  1. In Fenix, press SPC h x to open the Extensions page.
  2. Search for Python, and install it. Fenix shows what it may do before it installs anything.

Or download the package and run fenix --install-extension fenix.python-1.2.0.fenixext.

About

Python in Fenix: basedpyright as the language server with ruff's beside it, debugging with debugpy, ruff as the formatter, tasks, the project doctor's checks with their fixes, outdated and vulnerable packages, snippets, and Django and Flask projects in the new-project wizard. Built on lang-kit (crates/lang-kit), as each language pack is. It needs Fenix 1.5 or later (extension API 1.5); on an older Fenix, Python 1.1.0 is the one you get.

It works for a project uv manages (a uv.lock, or [tool.uv] in pyproject.toml) and for one it doesn't: then the venv's packages are uv's uv pip when there's uv, else the python3 on PATH (the venv's, when it's active) and its pip.

The language server

basedpyright's, basedpyright-langserver --stdio, when it's installed; else pyright's. python.server says which to prefer when both are. With neither, Fenix's own pyright-langserver is started as before, and the doctor's fix row installs basedpyright (uv tool install basedpyright, else pipx install, else pip install --user).

python.interpreter names a Python of your own: it's checked, runs the tasks and debugpy where there's no uv, and is the one the server is given (python.pythonPath), over the one Fenix finds.

Linting and formatting

ruff's server, ruff server, runs beside basedpyright: its problems as you type, and its fixes and code actions on SPC c a, with the server's. It needs ruff 0.5.3 or later (the doctor says).

With python.ruff = save, ruff check --output-format json runs on a file when it's saved instead, and its problems are shown with the server's: syntax errors and undefined names as errors, the rest as warnings, or what ruff says if milder. Its fixes are offered on SPC c a (one ruff calls unsafe says so); it never applies them (--no-fix), and a file the project excludes is left alone. off is neither.

SPC c F -- and saving, with editor.format_on_save -- runs ruff format on the buffer. The project's ruff (uv run ruff) when it asks for it, else the one installed; with none, nothing is set and the doctor offers to install it.

Debugging

The adapter is debugpy over stdio. In a project uv manages it's uv run --with debugpy python -m debugpy.adapter: uv brings debugpy into the project's environment for the session, so it needn't be a dependency. Without uv it's the Python's own, which needs pip install debugpy (a fix row).

SPC u u, in a project with no launch configuration of its own, offers:
Python: current filethe file you're in
Python: current file as a modulepython -m pkg.mod for the file you're in, so relative imports work
pytest: current file, pytest: all testspython -m pytest, with justMyCode off
Django: runservermanage.py runserver --noreload, templates debugged too
Flask: current fileflask --app <file> run, without Flask's debugger and reloader
FastAPI: current filefastapi dev <file> --no-reload
Python: attach (localhost:5678)to python -m debugpy --listen 5678 --wait-for-client app.py
Python: attach to a processto a Python running here, picked as it starts (${pickProcess}): debugpy is put into it by gdb (lldb on macOS)

pytest, Flask and FastAPI are debugpy's module, so no program is sent. The module one works the module out itself from the file, src/ left off, which Fenix's ${module} keeps.

Beside these, each of the project's scripts ([project.scripts]) is a launch of its own, Python: orbit (script), calling what it names (orbit.cli:main) as the script would; and a package with a __main__.py, Python: python -m orbit.

Tasks

SPC p t: run, test, lint, format, typecheck, and sync for a project uv manages. Each runs the project's own tool when it asks for it (uv run pytest), else one uv brings for the run (uv run --with pytest pytest), else what's installed. run is the project's first script, a Django project's runserver, a package's __main__.py, or main.py / app.py; test is manage.py test in a Django project without pytest-django; typecheck is mypy when the project has it, else basedpyright (or pyright). The project's .env goes to each. A task of the same name in .fenix/tools.json wins. Saving pyproject.toml, uv.lock or a requirements file makes them again.

Tests, for Fenix 1.6

Fenix 1.6 brings a test explorer, and this pack carries the test provider it will call: built and tested here, but not offered yet. Fenix asks for it only once this pack is released for extension API 1.6, after Fenix 1.6.0; until then nothing changes for you, on Fenix 1.5 as on a nightly. What it will do, as tested on pytest 9.2.0's recorded output (and run for real against it):

  • Find the tests in a file as you type, nothing run or imported: test* functions and Test* or unittest.TestCase classes, at their def's line, under their file and classes; @pytest.mark.skip (and unittest.skip, pytestmark = pytest.mark.skip(...)) as skipped; @pytest.mark.parametrize, and a fixture of the file's with params, as templates whose cases appear once listed or run. It reads python_files, python_classes and python_functions from the project's configuration. The cases, and what the scan can't see, come from pytest --collect-only, which imports every test module (so Fenix lists only in a project you trust).

  • Run one, a class, a file, everything or the failed ones: pytest's own node ids (tests/test_basic.py::test_cases[strings [odd] id]), as arguments, or in a file of ids when there are many. It runs uv run python in a project uv manages (--with pytest when the project doesn't ask for it), else the environment's Python, through a small plugin the pack ships (loaded with -p, nothing installed in your project), in the folder of pytest's configuration, with the project's .env. Where pytest.ini, pyproject.toml and the like are in several folders, each is a step of its own.

  • Read each result as it comes, with its time: a failure at its assertion, with its message, traceback and what the test printed; a fixture that raises as errored ("setup: ..."), as a teardown that raises after a pass; xfail as skipped with its reason, a strict xpass as failed; a file that doesn't load as "didn't load", never as failing tests (pytest then runs nothing); a process that dies as crashed, naming the test it was running. pytest-xdist works: the workers' results reach the plugin, interleaved, and a worker that dies errors its test.

  • Debug one test: debugpy's pytest module on its node id, in pytest's folder, as the pytest: current file launch.

The runner Fenix shows is pytest and its version, asked of the environment's Python as the pack starts (python -m pytest --version), or read from uv.lock; with pytest missing it says so. unittest-only projects run through pytest too, which collects unittest.TestCase.

What it can't: a test of a base class in another file isn't found as you type, only when listed or run; ids over 1 KiB (a parametrize with a huge string as its id) are run by their data, and, when Fenix has lost it, by their template; the first run of a project's uv run may sync its environment, as uv run pytest does; Windows isn't verified.

The project doctor

  • Python: the one uv would use (uv python find), else python3, held to requires-python (3.9 at least when it says none). Fix: uv python install.

  • uv: needed by a project it manages. Fix: pipx install uv, else pip install --user uv.

  • Environment: .venv in step with uv.lock (uv sync --locked --dry-run --offline): what differs, a lock that's out of date with pyproject.toml, or no .venv yet. Fix: uv sync.

  • Language server, ruff (unless the project has its own), debugpy (without uv), each with its install.

A fix that installs something is checked again, and what it installed is used at once.

Snippets

cls, dc (dataclass), main (if __name__ == "__main__"), def, adef, amain (asyncio.run), tg (a TaskGroup), with, cm and acm (contextlib's), cmc (__enter__/__exit__), test, atest, fixture, param, raises, prop, enum, proto, td (TypedDict), try, ann (from __future__ import annotations).

Project templates

Fenix's wizard already has uv's Python, a FastAPI service, a CLI (Typer, Click or argparse), a data project with notebooks and a desktop app; this adds:

  • Django site: settings from the environment (.env for development), one app with a page and its test, migrated; tests by pytest-django or manage.py test.

  • Flask app: an app factory, a blueprint with a page and a JSON route, tests with Flask's client.

Files

*.pyw, *.py3, *.wsgi, *.gyp, *.gypi, SConstruct, SConscript, wscript and .pythonrc are read as Python.

The lesson

SPC h T, Fenix's tutorial, has a lesson in its Python section, in a Python project of yours: the project doctor and a fix from it, the packages page, a task, a debug session stopped at a breakpoint, and ruff on save. Each step is checked by what's on screen -- the page or the picker in front -- and a step whose tool isn't installed yet is skipped with s on the tutorial page; the doctor says how to install it.

Keys

After SPC m in a Python project (C-k m with standard keys): p packages, d check again, s sync.
