Install

  1. In Fenix, press SPC h x to open the Extensions page.
  2. Search for Review, and install it. Fenix shows what it may do before it installs anything.

Or download the package and run fenix --install-extension fenix.review-1.2.0.fenixext.

About

Code review on GitHub and GitLab, without leaving Fenix: the pull and merge requests waiting, one under review with its files, threads, checks and the comments you're holding for it, sent with a verdict -- and a new pull request for the branch, prefilled from its commits.

It's the forge for Fenix's Git pages too: the Git status page's header says how the branch's request stands (its checks, approvals and open threads), and o there reviews it, or opens a new one.

KeyWhat it does
SPC g MThe reviews: open requests, yours, those waiting on you
SPC g PA pull request for the branch

With standard keys they're Ctrl+K g M and Ctrl+K g P. What it says names the keys as the key scheme in use has them, and yours when you've bound your own: "set one in C-," with standard keys, "in SPC ," with Vim keys. It needs Fenix 1.5 or later.

A review

KeyWhat it does
Tab, vOpen a file's diff; mark it viewed
C, SComment on the line or the lines marked, suggest a change -- held until you submit
r, RReply to a thread, resolve it
]tThe next thread
iOnly what changed since your last review
sSubmit: a approve, r request changes, c comment, e a summary, S S sends it. In the summary's box, A in Normal mode (Ctrl+Shift+A with standard keys) has your coding agent write it while the box is empty
mMerge: squash, rebase, delete the branch, when the checks pass; m m
w, o, qA worktree, the browser, close

A check's log opens as text; a failed one can run again. Your held comments and what you've seen are kept in the extension's data folder, so they wait for you across restarts.

A new request

The branch's commits against its base, whether it's pushed and merges cleanly, and the title, description (the repository's template, or the commits), reviewers and draft: Enter edits a field, e the description, S S pushes the branch if it has to and opens it. A branch named after a Jira issue puts the key in the title.

A in the description's box, in Normal mode (Ctrl+Shift+A with standard keys), has your coding agent write it, from the branch's change against its base and its commits, filling in the repository's template heading by heading. It works while the box is empty or still the template; with your text in it, A is Vim's. It's yours to edit before S S. The first time, Fenix asks whether the Review extension may send the branch's diff to that agent.

Once it's opened, a notification says so; Enter on it, or a click, opens the request in the browser.

Settings

Fenix's own, under Git and Forges (SPC ,, Ctrl+, with standard keys):

SettingWhat it does
git.base_branchThe branch requests go into (else the remote's default, main or master)
git.reviewersWho's asked to review a new request
gitlab.base_url, gitlab.tokenYour GitLab server, and a personal access token with the api scope
github.tokenGitHub's token, when the GitHub CLI isn't signed in (gh auth login)

A GitHub origin is GitHub's; any other is taken to be your GitLab.

Changelog

1.3.0

For Fenix 1.5 (extension API 1.5):

  • What it says names the keys of the key scheme in use, and yours when you've bound your own: "switch to one (C-k g w)" with standard keys, SPC g w with Vim keys, and C-, or SPC , where it sends you to Fenix's settings for a token, a GitLab server or the base branch.

  • A pull request opened is a notification, not a line in the message line: Enter on it, or a click, opens it in the browser. When asking its reviewers didn't work, the notification says so.

  • The README gives standard keys beside Vim's.

1.2.0

For Fenix 1.3 (extension API 1.4):

  • A in the box for your review's summary (s, e), in Normal mode while the box is empty, has your coding agent write it, going by the request, its diff and the comments you're holding. It's yours to edit before S S. With text in the box, A is Vim's.

  • A in a new request's description box does the same, from the branch's change and commits, in the repository's template. It writes over the template while that's untouched.

  • A on the review page is gone, and with it the agent's summary at the top of the page. So is a on a new request: the agent no longer writes the title.

1.1.1

Built against Fenix v1.1.0's released extension API, rather than the branch it was on before the release. Nothing changes in what it does.

1.1.0

For Fenix 1.1 (extension API 1.2):

  • a on a new request has your coding agent draft its title and description from the branch's change and commits, in the repository's template, for you to edit before you open it.

  • A on a review has your coding agent summarize the request: what it changes, what's risky, which files to read first. It's asked once per head while Fenix runs.

1.0.0

  • The first release, for Fenix 1.0: code review on GitHub and GitLab: the reviews waiting, a request with its files, threads, checks and your held comments, submitted with a verdict -- and a new pull request for the branch.
